Carga masiva y consultas de datos en Apache Cassandra

Simulación de más de un millón de mediciones ambientales

1 Abrir Docker Desktop

Antes de comenzar, abre Docker Desktop.

Espera a que el motor de Docker se encuentre funcionando.

Después abre:

  • PowerShell en Windows, o
  • Terminal en macOS.
Note

Los comandos de Docker que utilizaremos son prácticamente los mismos en Windows y macOS.

Lo que cambia principalmente es la ruta donde cada usuario guarda el archivo CSV.

2 Iniciar el contenedor de Cassandra

Inicia el contenedor que utilizamos en los ejercicios anteriores:

docker start cassandra-lab

El comando:

docker start

permite iniciar un contenedor que ya fue creado previamente.

En nuestro caso, el contenedor se llama:

cassandra-lab

Comprueba que se encuentre en ejecución:

docker ps

Deberá aparecer:

cassandra-lab

con un estado similar a:

Up
Note

Que el contenedor aparezca como Up significa que Docker ya lo inició.

Cassandra puede tardar algunos segundos adicionales en estar preparado para recibir conexiones.

3 Entrar a cqlsh

Para ingresar a la consola de Cassandra ejecuta:

docker exec -it cassandra-lab cqlsh

Podemos interpretar el comando así:

docker exec
    ↓
ejecutar un comando dentro del contenedor

-it
    ↓
permitir interacción desde la terminal

cassandra-lab
    ↓
nombre del contenedor

cqlsh
    ↓
consola interactiva de Cassandra

cqlsh significa:

Cassandra Query Language Shell

Cuando Cassandra esté disponible aparecerá:

cqlsh>

A partir de este momento, los comandos que escribamos se ejecutarán dentro de Cassandra.

4 Seleccionar el keyspace

Utilizaremos nuevamente el espacio de claves creado anteriormente:

USE monitoreo_ambiental;

El indicador deberá cambiar a:

cqlsh:monitoreo_ambiental>

Podemos revisar las tablas existentes:

DESCRIBE TABLES;

Deberán aparecer:

sensores
mediciones

5 Revisar la tabla mediciones

Antes de realizar la carga masiva revisaremos la tabla que almacenará las mediciones.

Ejecuta:

DESCRIBE TABLE mediciones;

La estructura utilizada es:

CREATE TABLE mediciones (
    sensor_id TEXT,
    fecha DATE,
    momento TIMESTAMP,
    temperatura DECIMAL,
    humedad DECIMAL,
    PRIMARY KEY ((sensor_id, fecha), momento)
) WITH CLUSTERING ORDER BY (momento DESC);

La parte más importante es:

PRIMARY KEY ((sensor_id, fecha), momento)

Podemos leerla en dos partes.

Primero:

(sensor_id, fecha)

indica en qué partición se guardará la información.

Después:

momento

indica cómo se organizarán las mediciones dentro de esa partición.

Por ejemplo:

(sensor_001, 2026-06-01)

corresponde a una partición.

Dentro de ella tendremos:

00:00
00:15
00:30
00:45
01:00
...
23:45

Es decir:

96 mediciones

del mismo sensor durante el mismo día.

En cambio:

(sensor_001, 2026-06-02)

corresponde a otra partición.

Y:

(sensor_002, 2026-06-01)

también corresponde a una partición distinta.

Important

La clave de partición no solamente identifica los datos.

También determina cómo Cassandra los organiza y distribuye.

Por lo tanto:

Trabajaremos con:

tendremos:

Cada partición tendrá:

        ↓

7 Generar el archivo CSV en Google Colab

Los datos no serán capturados manualmente.

Utilizaremos Python para generar automáticamente las mediciones.

El proceso será:

Python
    ↓
Generación de datos
    ↓
Archivo CSV

7.1 Importar las bibliotecas

En Google Colab ejecuta:

import csv
import random
import os
import pandas as pd

from datetime import datetime, timedelta
from google.colab import files

Utilizaremos:

csv

para crear el archivo.

random

para generar valores simulados.

datetime
timedelta

para trabajar con fechas e intervalos.

pandas

para verificar posteriormente el contenido del archivo.

7.2 Definir los parámetros

Ejecuta:

numero_sensores = 100

fecha_inicio = datetime(2026, 6, 1, 0, 0)

fecha_fin = datetime(2026, 10, 5, 23, 45)

intervalo = timedelta(minutes=15)

archivo = "mediciones_ambientales.csv"

Estamos indicando:

100 sensores

desde:

1 de junio de 2026

hasta:

5 de octubre de 2026

con una medición cada:

15 minutos

7.3 Calcular el número esperado de registros

Antes de generar el archivo podemos calcular cuántas filas esperamos obtener.

dias = (fecha_fin.date() - fecha_inicio.date()).days + 1

mediciones_por_dia = int(
    timedelta(days=1) / intervalo
)

total_registros = (
    numero_sensores
    * dias
    * mediciones_por_dia
)

print("Días:", dias)
print("Mediciones por día y sensor:", mediciones_por_dia)
print("Total esperado:", f"{total_registros:,}")

El resultado esperado es:

Días: 127
Mediciones por día y sensor: 96
Total esperado: 1,219,200

8 Generar las mediciones

Ahora construiremos el archivo CSV.

Ejecuta:

with open(archivo, "w", newline="", encoding="utf-8") as f:

    writer = csv.writer(f)

    writer.writerow([
        "sensor_id",
        "fecha",
        "momento",
        "temperatura",
        "humedad"
    ])

    momento_actual = fecha_inicio
    registros = 0

    while momento_actual <= fecha_fin:

        for sensor in range(1, numero_sensores + 1):

            sensor_id = f"sensor_{sensor:03d}"

            temperatura = round(
                random.uniform(18, 32),
                1
            )

            humedad = round(
                random.uniform(35, 80),
                1
            )

            writer.writerow([
                sensor_id,
                momento_actual.strftime("%Y-%m-%d"),
                momento_actual.strftime("%Y-%m-%d %H:%M:%S+0000"),
                temperatura,
                humedad
            ])

            registros += 1

        momento_actual += intervalo

print("Archivo generado correctamente")
print("Registros generados:", f"{registros:,}")

El resultado esperado es:

Archivo generado correctamente
Registros generados: 1,219,200

8.1 ¿Qué está haciendo el código?

El programa realiza tres pasos principales.

Primero genera información para los:

100 sensores

en un mismo momento.

Después ejecuta:

momento_actual += intervalo

Esto hace avanzar el reloj:

00:00
00:15
00:30
00:45
01:00
...

Después vuelve a generar información para los 100 sensores.

Este proceso continúa hasta llegar al:

5 de octubre de 2026 a las 23:45

La expresión:

f"sensor_{sensor:03d}"

permite crear identificadores como:

sensor_001
sensor_002
sensor_003
...
sensor_100

La temperatura se genera entre:

18 °C y 32 °C

y la humedad entre:

35 % y 80 %

8.2 Formato de momento

Observa especialmente esta línea:

momento_actual.strftime("%Y-%m-%d %H:%M:%S+0000")

Esto genera valores como:

2026-06-01 00:00:00+0000
2026-06-01 00:15:00+0000
2026-06-01 00:30:00+0000
2026-06-01 00:45:00+0000

Este formato permitirá que COPY FROM interprete correctamente los valores de tipo:

TIMESTAMP

17 Realizar la carga masiva

Ahora sí importaremos los registros.

Ejecuta:

COPY mediciones
(sensor_id, fecha, momento, temperatura, humedad)
FROM '/tmp/mediciones_ambientales.csv'
WITH HEADER = TRUE;

Podemos interpretarlo así:

Archivo CSV
      ↓
COPY FROM
      ↓
Tabla mediciones

La instrucción:

HEADER = TRUE

indica que la primera fila del CSV contiene los nombres de las columnas.

Note

COPY FROM es un comando proporcionado por cqlsh.

No debe confundirse con instrucciones CQL como:

SELECT
INSERT
UPDATE
DELETE

Durante la importación aparecerá información sobre los registros procesados.

Al finalizar esperamos observar algo similar a:

1219200 rows imported

y:

0 skipped

21 Consultar un intervalo de tiempo

También podemos utilizar:

momento

para consultar una parte del día.

Ejecuta:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-10-05'
  AND momento >= '2026-10-05T08:00:00Z'
  AND momento <= '2026-10-05T10:00:00Z';

Esta consulta recuperará únicamente las mediciones realizadas entre:

08:00

y:

10:00

El proceso puede entenderse así:

1. Cassandra recibe sensor_id y fecha
              ↓
2. Localiza la partición
              ↓
3. Utiliza momento
              ↓
4. Recupera solamente el intervalo solicitado

22 Comparar dos tipos de consulta

22.1 Consulta adecuada

Esta consulta utiliza completamente la clave de partición:

SELECT *
FROM mediciones
WHERE sensor_id = 'sensor_025'
  AND fecha = '2026-08-15';

Cassandra puede localizar directamente:

(sensor_025, 2026-08-15)

Conceptualmente:

1,219,200 registros
        ↓
Clave de partición
        ↓
Una partición
        ↓
96 registros

22.2 Consulta que no corresponde al diseño

Ahora imaginemos que queremos conocer todas las temperaturas superiores a:

30 °C

Podríamos intentar:

SELECT *
FROM mediciones
WHERE temperatura > 30;

Sin embargo:

temperatura

no forma parte de:

la clave de partición

ni de:

las columnas de agrupamiento

Por lo tanto, Cassandra no puede identificar directamente qué partición debe consultar.

23 ¿Qué es ALLOW FILTERING?

Podríamos escribir:

SELECT *
FROM mediciones
WHERE temperatura > 30
ALLOW FILTERING;

ALLOW FILTERING permite que Cassandra ejecute una consulta que puede requerir revisar y filtrar una gran cantidad de información.

WarningALLOW FILTERING no corrige un mal diseño

Que Cassandra permita ejecutar la consulta no significa que sea una buena estrategia.

Si nuestra aplicación necesitara consultar constantemente temperaturas superiores a cierto valor, lo adecuado sería diseñar otra tabla orientada específicamente a esa consulta.

La idea principal es:

primero identificamos las consultas
        ↓
después diseñamos las tablas
