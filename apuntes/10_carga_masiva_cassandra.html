Carga masiva y consultas de datos en Apache Cassandra

Simulación de más de 6 millones de mediciones ambientales

1 Introducción

En el apunte anterior trabajamos con Apache Cassandra utilizando una cantidad pequeña de registros para comprender los principales comandos de CQL, la creación de tablas, las claves de partición y las columnas de agrupamiento.

En esta práctica mantendremos el mismo sistema de monitoreo ambiental, pero aumentaremos considerablemente el volumen de información.

Simularemos mediciones generadas por 100 sensores, registrando temperatura y humedad cada 15 minutos, desde el 1 de enero de 2025 hasta el 5 de octubre de 2026.

Esto producirá:

100 sensores
×
643 días
×
96 mediciones por día
=
6,172,800 registros

El objetivo no será solamente cargar millones de registros.

También observaremos cómo Cassandra organiza esa información mediante particiones y cómo el diseño de la clave primaria permite realizar consultas eficientes.

Para ello utilizaremos diferentes herramientas:

Google Colab
    ↓
Python
    ↓
Archivo CSV
    ↓
Docker
    ↓
Apache Cassandra
    ↓
Consultas con CQL

Python se utilizará para generar los datos simulados.

Docker permitirá ejecutar Cassandra dentro de un contenedor.

Finalmente, Cassandra será utilizada para:

almacenar
+
organizar
+
consultar

la información.

3 1. Abrir Docker Desktop

Antes de comenzar, abre Docker Desktop.

Espera a que el motor de Docker se encuentre funcionando.

Después abre:

  • PowerShell en Windows, o
  • Terminal en macOS.
Note

Los comandos de Docker que utilizaremos durante esta práctica son prácticamente los mismos en Windows y macOS.

Lo que cambia principalmente es la ruta donde cada usuario almacena el archivo CSV.

Inicia el contenedor utilizado en los ejercicios anteriores:

El comando:

permite iniciar un contenedor que ya fue creado previamente.

7 5. Revisar la tabla mediciones

Antes de generar millones de registros revisaremos la estructura de la tabla que recibirá las mediciones.

Ejecuta:

DESCRIBE TABLE mediciones;

La estructura utilizada en el ejercicio anterior es:

CREATE TABLE mediciones (
    sensor_id TEXT,
    fecha DATE,
    momento TIMESTAMP,
    temperatura DECIMAL,
    humedad DECIMAL,
    PRIMARY KEY ((sensor_id, fecha), momento)
) WITH CLUSTERING ORDER BY (momento DESC);

La parte principal de nuestra tabla es:

PRIMARY KEY ((sensor_id, fecha), momento)

Podemos interpretarla así:

PRIMARY KEY

      ┌─────────────────────────┐
      │ Clave de partición      │
      │ (sensor_id, fecha)      │
      └─────────────────────────┘
                  +
      ┌─────────────────────────┐
      │ Columna de agrupamiento │
      │ momento                 │
      └─────────────────────────┘

La expresión:

(sensor_id, fecha)

es una clave de partición compuesta.

Mientras que:

momento

es una columna de agrupamiento o clustering column.

7.1 ¿Por qué utilizamos sensor_id y fecha?

Queremos que las mediciones correspondientes al mismo sensor y al mismo día se encuentren agrupadas dentro de una misma partición.

Por ejemplo:

(sensor_001, 2025-01-01)

representará una partición.

Dentro de ella encontraremos las mediciones de:

00:00
00:15
00:30
00:45
01:00
...
23:45

Pero:

(sensor_001, 2025-01-02)

será una partición diferente.

Y:

(sensor_002, 2025-01-01)

también será otra partición.

ImportantRecordatorio

En Cassandra la clave de partición no solamente identifica información.

También determina cómo se distribuyen y organizan los datos.

8 6. ¿Cómo se organizarán los datos?

Registraremos una medición cada:

15 minutos

En una hora tendremos:

4 mediciones

Por lo tanto:

4 mediciones por hora
×
24 horas
=
96 mediciones por día

Para cada sensor tendremos entonces:

96 registros por día

Para 100 sensores:

100 × 96
=
9,600 registros por día

Y durante 643 días:

9,600 × 643
=
6,172,800 registros

Sin embargo, estos registros no quedarán almacenados dentro de una sola partición.

La combinación:

(sensor_id, fecha)

generará:

100 sensores
×
643 días
=
64,300 particiones

Cada partición contendrá:

96 registros

Conceptualmente:

(sensor_001, 2025-01-01)
        ↓
     96 filas

(sensor_001, 2025-01-02)
        ↓
     96 filas

(sensor_002, 2025-01-01)
        ↓
     96 filas

Esta organización será importante cuando realicemos consultas.

9 7. Generar el archivo CSV en Google Colab

Los datos no serán capturados manualmente.

Utilizaremos Python para simular automáticamente las mediciones y generar un archivo CSV.

Abre Google Colab y crea una nueva libreta.

La secuencia será:

Python
    ↓
Generación automática de datos
    ↓
Archivo CSV

9.1 7.1 Importar las bibliotecas

En la primera celda escribe:

import csv
import random
from datetime import datetime, timedelta

Ejecuta la celda.

Utilizaremos:

csv

para crear y escribir el archivo CSV.

random

para generar valores aleatorios de temperatura y humedad.

Y:

datetime
timedelta

para trabajar con fechas, horas e intervalos de tiempo.

9.2 7.2 Definir los parámetros de la simulación

En una nueva celda escribe:

numero_sensores = 100

fecha_inicio = datetime(2025, 1, 1)
fecha_fin = datetime(2026, 10, 5, 23, 45)

intervalo = timedelta(minutes=15)

archivo = "mediciones_ambientales.csv"

Estamos indicando que la simulación utilizará:

100 sensores

desde:

2025-01-01 00:00

hasta:

2026-10-05 23:45

con un intervalo de:

15 minutos

El archivo resultante se llamará:

mediciones_ambientales.csv

9.3 7.3 Calcular cuántos registros se generarán

Antes de crear el archivo podemos calcular la cantidad esperada de registros.

Ejecuta:

dias = (fecha_fin.date() - fecha_inicio.date()).days + 1

mediciones_por_dia = int(
    timedelta(days=1) / intervalo
)

total_registros = (
    numero_sensores
    * dias
    * mediciones_por_dia
)

print("Días:", dias)
print("Mediciones por día y sensor:", mediciones_por_dia)
print("Total esperado:", f"{total_registros:,}")

El resultado esperado es:

Días: 643
Mediciones por día y sensor: 96
Total esperado: 6,172,800

De esta manera verificamos el volumen de información antes de comenzar la generación.

10 8. Generar las mediciones simuladas

Ahora construiremos el archivo CSV.

Podríamos pensar en crear primero una estructura con los más de seis millones de registros y después guardarla.

Sin embargo, esto consumiría una cantidad considerable de memoria.

En su lugar, escribiremos cada registro directamente en el archivo.

Ejecuta:

with open(archivo, "w", newline="", encoding="utf-8") as f:

    writer = csv.writer(f)

    writer.writerow([
        "sensor_id",
        "fecha",
        "momento",
        "temperatura",
        "humedad"
    ])

    momento_actual = fecha_inicio
    registros = 0

    while momento_actual <= fecha_fin:

        for sensor in range(1, numero_sensores + 1):

            sensor_id = f"sensor_{sensor:03d}"

            temperatura = round(
                random.uniform(18, 32),
                1
            )

            humedad = round(
                random.uniform(35, 80),
                1
            )

            writer.writerow([
                sensor_id,
                momento_actual.strftime("%Y-%m-%d"),
                momento_actual.strftime("%Y-%m-%dT%H:%M:%SZ"),
                temperatura,
                humedad
            ])

            registros += 1

        momento_actual += intervalo

print("Archivo generado correctamente")
print("Registros generados:", f"{registros:,}")

Al finalizar deberá aparecer:

Archivo generado correctamente
Registros generados: 6,172,800

10.1 ¿Qué está haciendo el código?

Primero crea el archivo:

mediciones_ambientales.csv

Después escribe los encabezados:

sensor_id
fecha
momento
temperatura
humedad

Posteriormente comienza en:

2025-01-01 00:00

y avanza en intervalos de:

15 minutos

Para cada momento genera información correspondiente a:

sensor_001
sensor_002
...
sensor_100

La expresión:

f"sensor_{sensor:03d}"

permite generar identificadores con tres dígitos.

Por ejemplo:

sensor_001
sensor_002
sensor_003
...
sensor_100

Los valores de temperatura se generan dentro del intervalo:

18 °C a 32 °C

y los valores de humedad entre:

35 % y 80 %
Note

El proceso puede tardar algunos minutos debido a la cantidad de registros que se están generando.

15 13. Copiar el archivo al contenedor

Actualmente tenemos dos espacios diferentes.

En nuestra computadora:

Computadora
    ↓
mediciones_ambientales.csv

Y dentro de Docker:

Docker
    ↓
cassandra-lab
    ↓
Apache Cassandra

El archivo almacenado en nuestra computadora no aparece automáticamente dentro del contenedor.

Por ello utilizaremos:

docker cp

Este comando permite copiar archivos entre nuestra computadora y un contenedor de Docker.

15.1 Windows

Si guardaste el archivo en:

C:\cassandra\mediciones_ambientales.csv

ejecuta en PowerShell:

docker cp "C:\cassandra\mediciones_ambientales.csv" cassandra-lab:/tmp/mediciones_ambientales.csv

15.2 macOS

Si el archivo se encuentra en Downloads, ejecuta:

docker cp ~/Downloads/mediciones_ambientales.csv cassandra-lab:/tmp/mediciones_ambientales.csv

En ambos casos estamos copiando el archivo hacia:

/tmp/mediciones_ambientales.csv

dentro del contenedor.

15.3 ¿Qué es /tmp?

/tmp es un directorio utilizado habitualmente en sistemas Linux para almacenar archivos temporales.

Nuestro contenedor utiliza un sistema basado en Linux, por ello podemos colocar temporalmente el CSV en:

/tmp

Conceptualmente:

Computadora

mediciones_ambientales.csv
          ↓
      docker cp
          ↓
Contenedor cassandra-lab

/tmp/mediciones_ambientales.csv
ImportantCopiar no significa importar

docker cp solamente copia el archivo hacia el sistema de archivos del contenedor.

Todavía no hemos cargado los registros a Cassandra.

La importación ocurrirá posteriormente mediante COPY FROM.

15.4 Comprobar que el archivo fue copiado

Podemos comprobar que el archivo existe dentro del contenedor mediante:

docker exec cassandra-lab ls -lh /tmp/mediciones_ambientales.csv

Aquí:

ls

permite listar archivos.

Y:

-lh

muestra información adicional y un tamaño más fácil de leer.

Deberá aparecer algo similar a:

-rw-r--r-- 1 root root ... /tmp/mediciones_ambientales.csv

17 15. Realizar la carga masiva

Ahora sí importaremos los datos hacia Cassandra.

Para ello utilizaremos:

COPY FROM

COPY es un comando proporcionado por cqlsh para importar o exportar información.

Note

COPY FROM pertenece a la herramienta cqlsh.

No debe confundirse con una instrucción del servidor CQL como SELECT, INSERT, UPDATE o DELETE.

Ejecuta:

COPY mediciones
(sensor_id, fecha, momento, temperatura, humedad)
FROM '/tmp/mediciones_ambientales.csv'
WITH HEADER = TRUE;

Podemos interpretarlo así:

Archivo CSV
        ↓
COPY FROM
        ↓
Tabla mediciones

Estamos indicando:

COPY mediciones

que los datos serán importados a la tabla:

mediciones

Después especificamos las columnas:

sensor_id
fecha
momento
temperatura
humedad

Y señalamos la ubicación del archivo:

/tmp/mediciones_ambientales.csv

Finalmente:

HEADER = TRUE

indica que la primera fila del CSV contiene los nombres de las columnas.

Warning

La operación puede tardar varios minutos porque estamos cargando más de seis millones de registros.

El tiempo dependerá de:

  • la velocidad de la computadora;
  • la memoria disponible;
  • los recursos asignados a Docker;
  • el procesador;
  • y el rendimiento del almacenamiento.

Durante la importación cqlsh mostrará información sobre los registros procesados.

En equipos con recursos limitados pueden aparecer mensajes temporales de espera o reintentos.

Lo importante será verificar al final que el proceso haya concluido correctamente.

Ejecuta:

SELECT *
FROM mediciones
WHERE sensor_id = 'sensor_001'

Esta consulta deberá recuperar las mediciones realizadas por:

sensor_001

durante:

2025-01-01

Como registramos una medición cada 15 minutos, esperamos encontrar:

96 registros

Podemos comprobarlo mediante:

SELECT COUNT(*)
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2025-01-01';

El resultado esperado es:

96

porque:

24 horas
×
4 mediciones por hora
=
96 mediciones

Aquí estamos consultando una sola partición:

(sensor_001, 2025-01-01)

19 17. Consultar una partición específica

Ahora podemos consultar otro sensor y otra fecha.

Por ejemplo:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_050'
  AND fecha = '2026-05-10';

Cassandra utilizará la clave:

(sensor_050, 2026-05-10)

para localizar la partición correspondiente.

Conceptualmente:

sensor_050
     +
2026-05-10
     ↓
Clave de partición
     ↓
Partición
     ↓
96 mediciones

La consulta no necesita recorrer los:

6,172,800 registros

para localizar esa información.

20 18. Consultar los registros más recientes

Recordemos que nuestra tabla fue definida mediante:

CLUSTERING ORDER BY (momento DESC)

DESC significa:

descendente

Por ello las mediciones dentro de cada partición se encuentran organizadas comenzando por las más recientes.

Podemos consultar únicamente las primeras 10:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-10-05'
LIMIT 10;

LIMIT 10 indica que solamente queremos recuperar:

10 filas

Debido al orden descendente, la primera deberá corresponder aproximadamente a:

23:45

seguida por:

23:30
23:15
23:00
22:45
...

21 19. Consultar un intervalo de tiempo

También podemos aprovechar la columna de agrupamiento:

momento

para consultar solamente una parte del día.

Por ejemplo:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-10-05'
  AND momento >= '2026-10-05T08:00:00Z'
  AND momento <= '2026-10-05T10:00:00Z';

Esta consulta recuperará las mediciones realizadas entre:

08:00

y:

10:00

La letra:

Z

indica que la hora fue expresada utilizando:

UTC

21.1 ¿Por qué funciona esta consulta?

Primero proporcionamos la clave de partición completa:

sensor_id + fecha

Por ejemplo:

(sensor_001, 2026-10-05)

Cassandra puede localizar la partición correspondiente.

Después aplicamos un intervalo sobre:

momento

que es nuestra columna de agrupamiento.

El proceso puede imaginarse así:

1. Identificar la clave de partición
              ↓
2. Localizar la partición
              ↓
3. Buscar dentro de la partición
              ↓
4. Aplicar el intervalo sobre momento
              ↓
5. Recuperar únicamente las filas solicitadas

22 20. Comparar diferentes consultas

La carga de millones de registros permite comprender mejor por qué el diseño de las tablas es tan importante en Cassandra.

22.1 Consulta adecuada

La siguiente consulta utiliza completamente la clave de partición:

SELECT *
FROM mediciones
WHERE sensor_id = 'sensor_025'
  AND fecha = '2026-03-15';

Cassandra puede identificar:

(sensor_025, 2026-03-15)

Conceptualmente:

6,172,800 registros
        ↓
Clave de partición
        ↓
(sensor_025, 2026-03-15)
        ↓
Una partición
        ↓
96 registros

Esta consulta corresponde directamente al diseño de nuestra tabla.

22.2 Consulta que no corresponde al diseño

Ahora imaginemos que queremos responder:

¿Cuáles fueron todas las mediciones con temperaturas superiores a 30 °C?

Podríamos intentar:

SELECT *
FROM mediciones
WHERE temperatura > 30;

Sin embargo:

temperatura

no forma parte de:

  • la clave de partición;
  • ni de las columnas de agrupamiento.

Por lo tanto, Cassandra no puede identificar directamente qué partición debe consultar.

En condiciones normales Cassandra rechazará esta consulta y mostrará un mensaje relacionado con:

ALLOW FILTERING

22.3 ¿Qué es ALLOW FILTERING?

Podríamos intentar:

SELECT *
FROM mediciones
WHERE temperatura > 30
ALLOW FILTERING;

La instrucción:

ALLOW FILTERING

le indica a Cassandra que permita una consulta que puede requerir revisar y filtrar una cantidad considerable de datos.

Sin embargo:

WarningALLOW FILTERING no corrige un mal diseño

Que Cassandra permita ejecutar una consulta mediante ALLOW FILTERING no significa que sea una buena estrategia.

Con grandes volúmenes de datos este tipo de consulta puede tener un rendimiento impredecible.

Si consultar temperaturas superiores a determinado valor fuera una necesidad frecuente de nuestra aplicación, lo apropiado sería diseñar una estructura adicional orientada específicamente a esa consulta.

ImportantDiseño orientado a consultas

En Cassandra normalmente no diseñamos primero una tabla genérica para posteriormente realizar cualquier consulta posible.

Primero identificamos:

¿Qué necesita consultar la aplicación?

y posteriormente diseñamos las tablas necesarias para responder esas consultas de manera eficiente.

27 25. Detener Cassandra

Cuando ya no necesitemos utilizar Cassandra podemos detener el contenedor.

Docker mostrará:

cassandra-lab

El contenedor dejará de ejecutarse, pero:

Esperamos algunos segundos y posteriormente:

Los datos almacenados continúan disponibles cuando volvamos a iniciarlo.

28 26. Para recordar

Durante esta práctica trabajamos con más de:

6 millones de registros

pero el aspecto más importante no fue únicamente el volumen.

También observamos cómo Cassandra organiza esa información.

Los principales puntos que debemos recordar son:

  • Python puede utilizarse para generar o preparar grandes cantidades de datos.
  • Google Colab permite ejecutar Python sin instalarlo localmente.
  • CSV es un formato sencillo para transportar información entre diferentes herramientas.
  • El programa genera los datos fila por fila para evitar almacenar millones de registros simultáneamente en memoria.
  • Docker ejecuta Cassandra dentro de un contenedor.
  • La computadora y el contenedor tienen sistemas de archivos diferentes.
  • docker cp permite copiar archivos desde nuestra computadora hacia el contenedor.
  • /tmp es un directorio temporal dentro del contenedor.
  • Copiar un archivo hacia Docker no significa que sus datos ya se encuentren almacenados en Cassandra.
  • COPY FROM es un comando de cqlsh que permite importar registros desde un archivo CSV.
  • HEADER = TRUE indica que la primera fila contiene los nombres de las columnas.
  • La tabla mediciones utiliza una clave de partición compuesta.
  • La clave de partición es (sensor_id, fecha).
  • Cada combinación de sensor y fecha corresponde a una partición diferente.
  • Tenemos 64,300 particiones.
  • Cada partición contiene 96 mediciones.
  • Los 6,172,800 registros se distribuyen entre esas particiones.
  • momento es una columna de agrupamiento.
  • momento permite ordenar y consultar intervalos dentro de una partición.
  • CLUSTERING ORDER BY (momento DESC) permite recuperar primero las mediciones más recientes.
  • LIMIT permite restringir la cantidad de filas devueltas.
  • Las consultas que utilizan la clave de partición corresponden directamente al diseño de nuestra tabla.
  • Las consultas arbitrarias sobre columnas como temperatura pueden requerir filtrado.
  • ALLOW FILTERING puede permitir determinadas consultas, pero no sustituye un buen diseño.
  • En Cassandra las tablas se diseñan principalmente de acuerdo con las consultas que necesita realizar la aplicación.
