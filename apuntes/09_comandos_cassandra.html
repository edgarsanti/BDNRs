Apache Cassandra: primeros comandos y consultas con CQL

Primeros comandos y ejemplo de monitoreo ambiental

1 Introducción

Apache Cassandra es una base de datos NoSQL distribuida que organiza la información mediante tablas diseñadas de acuerdo con las consultas que se necesitan realizar.

En este apunte utilizaremos CQL (Cassandra Query Language) para crear tablas, registrar datos y consultar las mediciones de una red de sensores ambientales.

Se da por hecho que Apache Cassandra ya fue instalado mediante Docker, como se explica en el manual de instalación del curso.

Para los ejemplos utilizaremos el contenedor:

cassandra-lab

A lo largo del apunte retomaremos el ejemplo de monitoreo ambiental utilizado anteriormente para observar cómo los conceptos de particionamiento, clave de partición y organización orientada a consultas se aplican directamente en Cassandra.

2 ¿Qué aprenderemos?

Al finalizar este apunte podrás:

  • Iniciar Apache Cassandra mediante Docker.
  • Acceder a la consola cqlsh.
  • Crear y seleccionar un keyspace.
  • Crear tablas mediante CQL.
  • Insertar, consultar, actualizar y eliminar registros.
  • Identificar una clave primaria.
  • Identificar una clave de partición.
  • Utilizar columnas de agrupamiento.
  • Diseñar una tabla para consultar el historial de mediciones de un sensor.
  • Comprender por qué en Cassandra las tablas se diseñan de acuerdo con las consultas que realizará la aplicación.

3 Iniciar Apache Cassandra

Antes de comenzar, abre Docker Desktop y espera a que el motor de Docker esté funcionando.

Después abre:

  • PowerShell en Windows, o
  • Terminal en macOS.

Los comandos de Docker que utilizaremos son los mismos en ambos sistemas.

Inicia el contenedor de Cassandra:

docker start cassandra-lab

Si el contenedor ya está iniciado, Docker mostrará nuevamente su nombre.

Para comprobar que se encuentra en ejecución:

docker ps

En la lista deberá aparecer:

cassandra-lab

con un estado similar a:

Up
NoteCassandra puede tardar unos segundos

Que el contenedor aparezca como Up significa que Docker ya lo inició.

Sin embargo, Cassandra puede tardar algunos segundos adicionales en estar preparado para recibir conexiones.

Si intentas acceder inmediatamente y aparece un mensaje parecido a:

Connection refused

espera unos segundos y vuelve a intentar la conexión.

4 Acceder a la consola de Cassandra

Para ingresar a Cassandra ejecuta:

docker exec -it cassandra-lab cqlsh

Cuando la conexión se complete aparecerá un indicador similar a:

cqlsh>

A partir de este momento, los comandos que escribamos se ejecutarán directamente en Cassandra.

Note¿Qué es cqlsh?

cqlsh significa Cassandra Query Language Shell.

Es una consola interactiva que permite ejecutar instrucciones CQL, de forma similar a:

  • mongosh en MongoDB.
  • redis-cli en Redis.

5 Comandos principales que utilizaremos

Antes de comenzar a trabajar, revisemos algunos de los principales comandos de CQL que utilizaremos durante este apunte.

Comando ¿Para qué sirve? Ejemplo
DESCRIBE KEYSPACES; Muestra los espacios de claves disponibles. DESCRIBE KEYSPACES;
CREATE KEYSPACE Crea un nuevo espacio de claves. CREATE KEYSPACE monitoreo_ambiental ...;
USE Selecciona el espacio de claves con el que vamos a trabajar. USE monitoreo_ambiental;
DESCRIBE TABLES; Muestra las tablas existentes. DESCRIBE TABLES;
CREATE TABLE Crea una nueva tabla. CREATE TABLE sensores (...);
DESCRIBE TABLE Muestra la definición de una tabla. DESCRIBE TABLE sensores;
INSERT INTO Inserta un registro. INSERT INTO sensores (...) VALUES (...);
SELECT Consulta información almacenada. SELECT * FROM sensores;
UPDATE Modifica valores de un registro. UPDATE sensores SET aula = '102' WHERE sensor_id = 'sensor_001';
DELETE Elimina un registro o determinados valores. DELETE FROM sensores WHERE sensor_id = 'sensor_004';
COUNT(*) Cuenta los registros que devuelve una consulta. SELECT COUNT(*) FROM sensores;
exit; Cierra la consola cqlsh. exit;
ImportantCQL se parece a SQL, pero Cassandra funciona diferente

CQL utiliza instrucciones que pueden resultar familiares para quienes han trabajado con SQL.

Sin embargo, Cassandra no funciona como una base de datos relacional tradicional.

El diseño de las tablas y las consultas depende especialmente de:

  • las claves de partición;
  • las columnas de agrupamiento;
  • y las consultas que necesita realizar la aplicación.

6 Explorar los espacios de claves

En Cassandra, un keyspace o espacio de claves agrupa las tablas de una aplicación y establece su configuración de replicación.

Podemos pensar en él como el espacio principal donde almacenaremos las tablas relacionadas con nuestro sistema.

Para consultar los espacios de claves disponibles:

DESCRIBE KEYSPACES;

Al instalar Cassandra aparecen varios espacios utilizados internamente por el sistema.

Por ejemplo:

system
system_auth
system_schema
system_distributed

No modificaremos estos espacios.

Crearemos uno propio para nuestro ejemplo.

7 Crear un keyspace

Nuestro sistema almacenará información relacionada con sensores ambientales.

Crearemos un espacio denominado:

monitoreo_ambiental

Ejecuta:

CREATE KEYSPACE IF NOT EXISTS monitoreo_ambiental
WITH replication = {
    'class': 'SimpleStrategy',
    'replication_factor': 1
};

En este ejemplo utilizamos:

SimpleStrategy

y un factor de replicación de:

1

porque estamos trabajando con un único nodo de Cassandra dentro de Docker.

WarningConfiguración de aprendizaje

SimpleStrategy y un factor de replicación de 1 son suficientes para este ejercicio.

No deben interpretarse como una configuración recomendada para un sistema de producción con múltiples nodos.

Selecciona el keyspace:

USE monitoreo_ambiental;

El indicador cambiará a:

cqlsh:monitoreo_ambiental>

Esto indica que los siguientes comandos se ejecutarán dentro de este espacio de claves.

8 Crear la tabla de sensores

Primero almacenaremos la información general de cada sensor.

Queremos conservar:

  • Identificador.
  • Edificio.
  • Aula o zona.
  • Tipo de medición.

Crearemos la tabla:

CREATE TABLE IF NOT EXISTS sensores (
    sensor_id TEXT PRIMARY KEY,
    edificio TEXT,
    aula TEXT,
    tipo TEXT
);

En esta tabla:

sensor_id

es la clave primaria.

Su función es identificar de manera única cada sensor.

Por ejemplo:

sensor_001
sensor_002
sensor_003

No debemos utilizar el mismo identificador para dos sensores diferentes.

8.1 Consultar las tablas existentes

Ejecuta:

DESCRIBE TABLES;

Deberá aparecer:

sensores

También podemos consultar la definición completa de la tabla:

DESCRIBE TABLE sensores;

9 Insertar registros

Registraremos tres sensores instalados en diferentes espacios de una universidad.

INSERT INTO sensores (sensor_id, edificio, aula, tipo)
VALUES ('sensor_001', 'A', '101', 'Temperatura y humedad');

INSERT INTO sensores (sensor_id, edificio, aula, tipo)
VALUES ('sensor_002', 'A', 'Laboratorio', 'Temperatura y humedad');

INSERT INTO sensores (sensor_id, edificio, aula, tipo)
VALUES ('sensor_003', 'B', 'Exterior', 'Temperatura');

Cada instrucción INSERT INTO agrega información asociada con una clave primaria.

10 Consultar los sensores

Para consultar todos los registros:

SELECT * FROM sensores;

Podríamos obtener un resultado similar a:

 sensor_id   | edificio | aula         | tipo
-------------+----------+--------------+------------------------
 sensor_001  | A        | 101          | Temperatura y humedad
 sensor_002  | A        | Laboratorio  | Temperatura y humedad
 sensor_003  | B        | Exterior     | Temperatura

El orden de las filas puede ser diferente al orden en el que fueron insertadas.

10.1 Consultar un sensor específico

Podemos utilizar su clave primaria:

SELECT * FROM sensores
WHERE sensor_id = 'sensor_001';

10.2 Seleccionar únicamente algunas columnas

SELECT sensor_id, edificio, aula
FROM sensores
WHERE sensor_id = 'sensor_002';

11 Actualizar registros

Supongamos que el sensor sensor_001 fue trasladado del aula 101 al aula 102.

Podemos modificar su ubicación mediante:

UPDATE sensores
SET aula = '102'
WHERE sensor_id = 'sensor_001';

Comprueba el cambio:

SELECT * FROM sensores
WHERE sensor_id = 'sensor_001';
ImportantConsideración sobre UPDATE

En Cassandra, UPDATE también puede crear una fila si no existe un registro con la clave primaria indicada.

Por esta razón, debemos revisar cuidadosamente la clave utilizada antes de ejecutar una actualización.

12 Eliminar registros

Para practicar la eliminación sin perder nuestros tres sensores principales, agregaremos temporalmente un cuarto sensor:

INSERT INTO sensores (sensor_id, edificio, aula, tipo)
VALUES ('sensor_004', 'C', 'Almacén', 'Temperatura');

Comprueba que existe:

SELECT * FROM sensores
WHERE sensor_id = 'sensor_004';

Ahora elimínalo:

DELETE FROM sensores
WHERE sensor_id = 'sensor_004';

Comprueba nuevamente:

SELECT * FROM sensores
WHERE sensor_id = 'sensor_004';

Si la eliminación se realizó correctamente, la consulta no devolverá filas.

13 Del registro de sensores al historial de mediciones

Hasta ahora tenemos una tabla que permite responder preguntas como:

¿Dónde se encuentra el sensor 001?

o:

¿Qué tipo de información registra el sensor 002?

Sin embargo, todavía no podemos responder una pregunta diferente:

¿Qué temperaturas registró el sensor 001 durante un día determinado?

El problema es que un sensor genera muchas mediciones a lo largo del tiempo.

Por ejemplo:

sensor_001

09:00 → 22.4 °C
09:05 → 22.8 °C
09:10 → 23.1 °C

No queremos reemplazar la temperatura anterior cada vez que recibimos una nueva lectura.

Necesitamos conservar el historial de mediciones.

Para ello crearemos una segunda tabla.

14 Diseñar la tabla a partir de la consulta

Antes de crear la tabla debemos recordar una idea fundamental de Cassandra:

Primero pensamos qué consulta necesita realizar la aplicación y después diseñamos la tabla.

En nuestro ejemplo queremos responder principalmente:

¿Cuáles fueron las mediciones de un sensor durante una fecha determinada?

Para ello utilizaremos:

sensor_id + fecha

para agrupar las lecturas correspondientes al mismo dispositivo y día.

Dentro de cada grupo utilizaremos:

momento

para ordenar las diferentes mediciones.

15 Crear la tabla de mediciones

Ejecuta:

CREATE TABLE IF NOT EXISTS mediciones (
    sensor_id TEXT,
    fecha DATE,
    momento TIMESTAMP,
    temperatura DECIMAL,
    humedad DECIMAL,
    PRIMARY KEY ((sensor_id, fecha), momento)
) WITH CLUSTERING ORDER BY (momento DESC);

Esta tabla presenta una estructura más interesante que la tabla sensores.

La parte principal es:

PRIMARY KEY ((sensor_id, fecha), momento)

Podemos interpretarla así:

┌──────────────────────────────┐
│ Clave de partición           │
│ (sensor_id, fecha)           │
└──────────────────────────────┘
              +
┌──────────────────────────────┐
│ Columna de agrupamiento      │
│ momento                      │
└──────────────────────────────┘

16 Clave de partición

La expresión:

(sensor_id, fecha)

constituye una clave de partición compuesta.

Esto significa que las lecturas que tienen el mismo:

sensor_id

y la misma:

fecha

pertenecen a la misma partición lógica.

Por ejemplo:

(sensor_001, 2026-09-29)

    09:00 → 22.4 °C
    09:05 → 22.8 °C
    09:10 → 23.1 °C

Estas tres mediciones pertenecen a la misma partición.

Sin embargo:

(sensor_001, 2026-09-30)

corresponde a una partición diferente.

También:

(sensor_002, 2026-09-29)

corresponde a otra partición.

NoteRelación con el apunte anterior

En el tema de familias de columnas observamos conceptualmente combinaciones como:

(sensor_001, 2026-09-29)

Ahora estamos utilizando esa misma idea directamente en Cassandra mediante una clave de partición compuesta.

17 Columna de agrupamiento

La columna:

momento

es una columna de agrupamiento (clustering column).

Su función es:

  1. distinguir las diferentes filas dentro de una misma partición;
  2. organizar las mediciones por fecha y hora.

La instrucción:

CLUSTERING ORDER BY (momento DESC)

indica que las mediciones se mostrarán comenzando por las más recientes.

Por ejemplo:

09:10 → 23.1 °C
09:05 → 22.8 °C
09:00 → 22.4 °C
Tip¿Por qué utilizar dos tablas?

La tabla sensores responde preguntas relacionadas con la información general de cada dispositivo.

La tabla mediciones responde preguntas relacionadas con el historial de lecturas.

En Cassandra es normal tener diferentes tablas diseñadas para diferentes consultas.

18 Registrar mediciones de temperatura y humedad

Insertaremos tres mediciones para sensor_001.

Utilizaremos horas expresadas en UTC mediante la letra Z.

INSERT INTO mediciones
(sensor_id, fecha, momento, temperatura, humedad)
VALUES
('sensor_001', '2026-09-29', '2026-09-29T09:00:00Z', 22.4, 45.0);

Segunda medición:

INSERT INTO mediciones
(sensor_id, fecha, momento, temperatura, humedad)
VALUES
('sensor_001', '2026-09-29', '2026-09-29T09:05:00Z', 22.8, 46.0);

Tercera medición:

INSERT INTO mediciones
(sensor_id, fecha, momento, temperatura, humedad)
VALUES
('sensor_001', '2026-09-29', '2026-09-29T09:10:00Z', 23.1, 44.0);

También registraremos una lectura del segundo sensor:

INSERT INTO mediciones
(sensor_id, fecha, momento, temperatura, humedad)
VALUES
('sensor_002', '2026-09-29', '2026-09-29T09:00:00Z', 21.7, 48.0);

El sensor exterior únicamente registra temperatura.

Por ello podemos omitir la columna humedad:

INSERT INTO mediciones
(sensor_id, fecha, momento, temperatura)
VALUES
('sensor_003', '2026-09-29', '2026-09-29T09:00:00Z', 25.6);

En este caso no existe un valor registrado para humedad.

Esto permite observar que una fila no necesita tener valores en todas las columnas que no forman parte de la clave primaria.

19 Consultar el historial de un sensor

Ahora podemos realizar la consulta para la cual diseñamos nuestra tabla.

SELECT * FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-09-29';

La consulta recuperará las tres mediciones del sensor durante ese día.

Como definimos:

CLUSTERING ORDER BY (momento DESC)

las mediciones aparecerán de la más reciente a la más antigua.

Conceptualmente:

09:10 → 23.1 °C
09:05 → 22.8 °C
09:00 → 22.4 °C

20 Seleccionar únicamente algunas columnas

Podemos recuperar solamente la información que necesitamos:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-09-29';

21 Contar las mediciones

Podemos comprobar cuántas mediciones existen dentro de esa partición:

SELECT COUNT(*)
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-09-29';

El resultado esperado es:

3

22 Consultar un intervalo de tiempo

También podemos utilizar la columna de agrupamiento para consultar solamente una parte del historial.

Por ejemplo:

SELECT momento, temperatura, humedad
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-09-29'
  AND momento >= '2026-09-29T09:05:00Z';

Esta consulta recuperará las mediciones realizadas a partir de las 09:05.

Conceptualmente:

09:10 → 23.1 °C
09:05 → 22.8 °C

Esto es posible porque momento es una columna de agrupamiento dentro de la partición.

23 ¿Todas las consultas son posibles?

Nuestra tabla fue diseñada específicamente para consultar:

sensor + fecha

Por ejemplo:

SELECT *
FROM mediciones
WHERE sensor_id = 'sensor_001'
  AND fecha = '2026-09-29';

Esta consulta se adapta perfectamente al diseño de la tabla.

Sin embargo, podríamos imaginar otra pregunta:

¿Cuáles son todas las mediciones con una temperatura superior a 25 °C?

Podríamos pensar en escribir:

SELECT *
FROM mediciones
WHERE temperatura > 25;

Sin embargo, nuestra tabla no fue diseñada específicamente para realizar esa consulta de forma eficiente.

WarningDiseñar según la consulta

En Cassandra no todas las consultas que parecen naturales en SQL pueden realizarse eficientemente sobre cualquier tabla.

Si consultar temperaturas superiores a determinado valor fuera una necesidad frecuente de nuestra aplicación, probablemente tendríamos que diseñar otra tabla preparada para responder esa consulta.

Por esta razón evitaremos utilizar ALLOW FILTERING como solución habitual.

24 Comparación de nuestras dos tablas

Durante este apunte construimos dos tablas con propósitos diferentes.

Tabla Propósito principal
sensores Consultar información general de un dispositivo
mediciones Consultar el historial de un sensor durante una fecha

La tabla:

sensores

utiliza:

sensor_id

como clave primaria.

La tabla:

mediciones

utiliza:

(sensor_id, fecha)

como clave de partición y:

momento

como columna de agrupamiento.

Esta diferencia refleja una de las ideas principales de Cassandra:

Las tablas se diseñan de acuerdo con las consultas que necesita realizar la aplicación.

25 Cerrar la sesión

Para salir de cqlsh:

exit;

Regresarás a PowerShell o Terminal.

26 Detener Cassandra

Para detener el contenedor:

docker stop cassandra-lab

Docker mostrará:

cassandra-lab

El contenedor dejará de ejecutarse, pero no será eliminado.

Los datos permanecerán almacenados mientras el contenedor continúe existiendo.

Cuando quieras trabajar nuevamente con Cassandra:

docker start cassandra-lab

Espera unos segundos y accede nuevamente mediante:

docker exec -it cassandra-lab cqlsh

27 Para recordar

  • Docker Desktop permite ejecutar Cassandra dentro de un contenedor.
  • CQL es el lenguaje utilizado para interactuar con Cassandra.
  • cqlsh es la consola donde ejecutamos instrucciones CQL.
  • Un keyspace agrupa las tablas de una aplicación.
  • Una clave primaria identifica y organiza las filas.
  • La clave de partición determina qué registros pertenecen a una misma partición.
  • Una clave de partición puede estar formada por más de una columna.
  • Las columnas de agrupamiento organizan las filas dentro de una partición.
  • Cassandra favorece un diseño de tablas pensado a partir de las consultas.
  • Diferentes consultas pueden requerir diferentes tablas.

28 ¿En qué situaciones podríamos utilizar este modelo?

Las bases de datos de familias de columnas pueden resultar útiles cuando una aplicación genera grandes cantidades de registros y necesita almacenar o consultar información de manera distribuida.

La siguiente tabla muestra algunos ejemplos.

Aplicación Datos que podría almacenar ¿Por qué podría utilizarse?
Monitoreo ambiental Temperatura, humedad y estado de sensores Los dispositivos generan mediciones constantemente y es necesario conservar su historial
Internet de las cosas (IoT) Lecturas de sensores, dispositivos y eventos Puede recibir grandes cantidades de registros provenientes de numerosos dispositivos
Monitoreo de servidores Uso de CPU, memoria, almacenamiento y eventos Los servidores generan métricas continuamente a lo largo del tiempo
Telecomunicaciones Registros de llamadas, conexiones y eventos de red Puede producir grandes volúmenes de información de manera continua
Plataformas digitales Eventos de navegación, reproducciones o interacciones Las acciones de los usuarios pueden generar millones de eventos
Sistemas de transporte Posición, velocidad y estado de vehículos Cada vehículo puede enviar información constantemente
Medidores inteligentes Consumo eléctrico, agua o gas Se generan mediciones periódicas que deben conservarse históricamente
Registros de aplicaciones Eventos, errores y actividad de los sistemas Puede ser necesario almacenar grandes cantidades de registros para su posterior análisis
NoteUn patrón común

En muchos de estos ejemplos encontramos una situación similar:

Muchos dispositivos o usuarios
            ↓
Generación continua de datos
            ↓
Gran cantidad de registros
            ↓
Necesidad de consultar información histórica

Este tipo de escenario puede beneficiarse de tecnologías distribuidas como Apache Cassandra.

Sin embargo, esto no significa que Cassandra sea la mejor opción para cualquier aplicación.

Si un sistema necesita realizar numerosas relaciones entre entidades, consultas muy variables o múltiples operaciones mediante JOIN, una base de datos relacional puede resultar más adecuada.

La elección de la tecnología debe depender siempre de:

  • la estructura de los datos;
  • el volumen de información;
  • la velocidad con la que se generan nuevos registros;
  • las consultas que necesita realizar la aplicación;
  • y la forma en que se espera que el sistema crezca.
